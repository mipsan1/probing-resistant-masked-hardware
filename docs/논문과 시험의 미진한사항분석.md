# 결론

## 1. 프로그램은 정상입니다 — 버그가 아닙니다

d=2 프로브 공간이 **C(25,536,2) = 3.26억 개**로 d=1(14,400개)의 약 22,600배입니다. PROLEAD가 이를 배치당 ~200만 개씩 **164개 배치**로 쪼개고, 배치 1개가 **1시간 17분**이므로 전체 **약 8.8일**이 걸리는 것이 정상 사양입니다.

- "batch=1을 넘지 못하는" 이유 = 배치 1개 자체가 77분이라서 + 재시작할 때마다 처음부터 다시 시작하기 때문 (resume 기능 없음)
- 메모리 6.985 GB로 안정적 → 비정상 종료 아님
- batch 1에서 32k 시뮬레이션 시 LEAKAGE → 64k에서 OKAY로 바뀌는 것도 추정기 노이즈 플리커로, 논문 본인들이 §partial-d2에 직접 설명한 정상 현상

**해야 할 일**: tmux/서버에 붙여놓고 그냥 9일 돌리거나, d=2 검증 대상을 S-box 코어로 축소(프로브 수가 줄면 제곱으로 시간 감소), 둘 중 하나입니다.

## 2. 제출 가능 여부 — 현 상태로는 위험합니다

**판정: 지금 내면 TIFS 기준 Major Revision 가능성이 높고, accept-range(목표 80/100)에는 미달입니다.**

**강점** (살아있는 것들):

- Soundness gap + cone non-completeness + lint + 명시적 witness라는 "틈새 발견→증명→수정" 스토리가 명확
- 완전 시뮬레이션 증명(SD=0) + 공개 PROLEAD + TVLA 3채널 교차 검증
- 아티팩트 공개, 양성 대조군(비마스킹 회로는 결정적으로 누설) — 검출기 신뢰성 입증됨

**치명적 구멍** (리뷰어가 반드시 공격할 지점):

1. **d=2 커버리지 2.5%(4/164 배치) + "future work" 표기** — 이게 제일 큽니다. Table에서 d=2의 TVLA/MI 칸이 비어 있고, "부분 스윕"이라고 쓴 순간 리뷰어는 "그럼 d=2 주장은 미검증"이라고 읽습니다. Bonferroni 논증은 귀무분포 하 기댓값일 뿐 나머지 97.5%의 안전성을 보이지 못합니다.
2. **Novelty 포지셔닝** — DOM, Itoh–Tsujii, PROLEAD는 전부 기존 도구입니다. "value-based 검증이 글리치 재결합을 놓친다"는 것이 maskVerif/SILVER 계열 문헌 대비 새 발견인지, 알려진 사실의 재확인인지를 Related Work에서 선제적으로 방어하지 않으면 기여가 "린트 도구 하나"로 축소돼 보입니다.
3. **"10-Round Extension (Skeleton)"** — 제목에 skeleton이라고 쓴 섹션은 미완성 선언입니다. 완성하거나 빼야 합니다.
4. TVLA N=10⁴는 관행(10⁵~10⁷) 대비 작음 — 시뮬레이션 기반이라 방어 가능하지만 한 줄 각도가 필요합니다.

## 액션 우선순위

1. **d=2 스윕을 끝내는 것이 최우선** — 8.8일 풀런(서버에 상주 실행) 또는 코어 축소 풀 검증. 이 하나로 최대 감점 요인이 사라집니다.

3. Related Work에서 value-based vs glitch-robust 불일치의 선행 사례를 정리하고 차별점을 명문화.

# d=2가 진행되지 않는 이유 — 원인 분석

데이터로 확인한 결과, **멈춘 것이 아니라 batch 1 하나가 통째로 77분짜리 작업이라 진행이 안 보이는 것**입니다. 원인은 4가지가 겹쳐 있습니다.

## 원인 1: 프로브 공간의 제곱 폭발 (근본 원인)

|  | d=1 | d=2 |
| --- | --- | --- |
| 프로브 집합 | 14,400개 (단일 프로브) | C(25,536, 2) = **326,030,880개** (모든 쌍) |
| 배치 | 1개 | **~164개** (배치당 1,997,984세트) |

2차 probing은 "프로브 2개의 모든 조합"이라서, 25,536개 프로브가 3.26억 개 쌍으로 폭발합니다. d=1 대비 **22,600배** 작업량입니다. 이건 설정 오류가 아니라 order-2 검증의 수학적 본질입니다.

## 원인 2: 배치 1개의 내부 작업량이 1,280억 회

방금 probes 파일에서 계산한 수치:

- 배치 1개 = 1,997,984세트 × 64,000 시뮬레이션 = **1.28×10¹¹ 회의 세트-시뮬레이션**
- 초당 약 2,770만 회를 처리해도 **77분** 소요
- 글리치 확장 콘은 평균 2신호/프로브로 작아서(최대도 2), 콘 크기가 병목은 아님 — 순수하게 **쌍의 개수**가 병목

즉 실행 직후 최소 77분간은 "batch 1" 화면만 보이는 게 정상이고, 이 창 안에서 판단하면 영원히 진행이 없어 보입니다.

## 원인 3: 재시작 = 항상 batch 1로 회귀

PROLEAD는 체크포인트/resume이 없습니다. "멈춘 것 같아서" 죽이고 다시 돌리면 **무조건 batch 1부터**입니다. 반복 재시작 패턴이었다면 실제로는 진행 중이었는데 매번 0으로 리셋한 셈입니다.

## 원인 4: batch 1 도중 뜨는 가짜 LEAKAGE가 재시작을 유도

- d=2에서는 배치당 세트가 200만 개라 p<10⁻⁵ 수준의 우연 양성이 **배치당 약 20개 기대**됩니다 (d=1 때는 고정 임계값 5가 sound했지만, d=2에서는 Bonferroni 기준 7.6016이어서 고정 임계값 5가 깨짐 — 논문 부록에 직접 지적한 내용)
- 실제로 fixB batch 1 기록: 32k 시뮬레이션에서 **LEAKAGE** (−log₁₀p=5.19) → 48k에서 OKAY(4.33) → 64k에서 OKAY(3.98)
- 진짜 누설은 트레이스가 늘수록 강해지는데, 이건 약해지며 사라지는 전형적 추정기 노이즈입니다. **하지만 32k 시점의 LEAKAGE를 보고 "설계가 잘못됐다"며 중단·재시작하면 역시 batch 1을 못 벗어납니다.**

## 종합

```
제곱 폭발(3.26억 쌍) → 배치당 1.28×10¹¹ 회 연산 → 배치 1개 = 77분
+ resume 없음 + 도중 가짜 LEAKAGE
= 몇 번을 돌려도 batch 1만 보임 (정상 동작)
```

메모리는 6.985 GB로 안정적이고, 4개 배치를 완료한 기록이 논문에 있는 것으로 봐서 **붙여놓고 두면 진행됩니다.** 해결은 ① 서버/tmux에서 끄지 않고 ~9일 연속 실행, ② 검증 대상을 S-box 코어로 축소(프로브 수가 줄면 시간이 제곱으로 감소 — 예: 프로브 1/5로 줄이면 25배 빨라짐), ③ 실행 로그에서 배치 진행 표시가 찍히는지 확인 후 그대로 두기, 셋 중 하나입니다.


좋은 직감입니다 — 다만 "20%"를 어떻게 뽑느냐가 논문 방어의 핵심이라, 정확한 수치부터 확인하겠습니다.

# 결론: 네, 20%면 충분히 방어 가능합니다 — 단, 조건 3개를 지켜야 합니다

방금 계산한 수치로 답합니다.

## 시간 산수 — 20%가 현실적 최적점인 이유

| 커버리지 | 배치 수 | 소요 시간 |
| --- | --- | --- |
| 2.5% (현재) | 4 | 5시간 |
| **20%** | **33** | **약 42시간 (1.8일)** |
| 50% | 82 | 4.4일 |
| 100% | 164 | 8.8일 |

20%는 이틀이면 끝납니다. 현재 2.5%와 100% 사이에서 비용 대비 방어력이 가장 좋은 지점이 맞습니다.

## 조건 1: "처음 33개 배치"를 돌리면 안 됩니다 (가장 중요)

PROLEAD 배치는 프로브 쌍을 사전식 순서로 쪼갠 것이라, **처음 33개 배치 = 앞쪽 프로브 11,483개(45%) 내부의 쌍만 검사하고, 나머지 55% 프로브가 포함된 쌍은 커버리지 0%**입니다. 이러면 리뷰어가 "뒤쪽 파이프라인 단계는 하나도 검증 안 했네"라고 반박할 수 있습니다.

→ **전체 프로브 공간에서 무작위/층화 추출로 20%를 뽑아야** 합니다. 예: 프로브를 무작위로 45% 서브샘플링하면 쌍 커버리지 20%(0.45²)가 되면서 회로 전 구간에 고르게 분포합니다. 같은 42시간인데 편향이 사라집니다.

## 조건 2: 통계적 한계를 논문에 명시해야 합니다

0 누설 관측 시 95% 신뢰 상한(rule of three, 3/f):

- 현재 2.5%: 전체에 최대 **120개** 누설 세트가 숨어있을 수 있음 → 약함
- **20%: 최대 15개 (누설률 4.6×10⁻⁸)** → 강함
- 그리고 만약 설계 결함이 구조적이라면(쌍의 0.001%만 오염돼도) 무작위 20% 샘플에서 **검출 확률 사실상 100%**입니다

즉 20%는 "완전 검증"이 아니라 "구조적 결함은 확실히 걸러내고, 잔여 리스크는 고립 세트 15개 이하로 한정"하는 검증입니다. 보안 주장이全称 명제(모든 쌍이 안전)이므로 이 한계를 숨기면 리뷰어에게 걸리고, 위 수치를 표로 제시하면 오히려 엄밀성 점수를 받습니다.

## 조건 3: 포지셔닝을 바꿔야 합니다

- 지금 논문은 "partial sweep, complete sweep은 future work" — 스스로 미완성이라고 선언한 셈이라 리뷰어가 공격하기 쉽습니다.
- 20%를 돌린 뒤 문장을 이렇게 재구성: **"정리(완전 시뮬레이션 증명)가 전체 프로브 공간을 수학적으로 커버하고, PROLEAD 무작위 층화 스윕(6.6×10⁷/3.26×10⁸ 세트, 0 누설, 잔여 상한 15세트@95%)은 이를 실증적으로 확증한다"** — 주(主) 증거는 증명, PROLEAD는 corroboration. 이 구조면 d=2 실험 공백 논란이 사라집니다.

## 최종 답변

**20%로 제출 가능합니다.** 다만 ① 무작위/층화 추출(연속 배치 X), ② 잔여 상한 15세트 통계 명시, ③ "partial → sampled verification" 재포지셔닝, 이 세 가지를 반영한 20%여야 합니다. 현재 상태(연속 4배치, 2.5%, "future work" 표기)는 약하지만, 42시간 투자 + 문장 수정으로 accept-range 진입이 가능한 수준까지 올라갑니다. 시간적 여유가 있다면 8.8일 풀 스윕이 물론 금본위이지만, 20%도 충분히 심사를 통과할 수 있는 근거가 됩니다.

실험 설계의 핵심 산출물(재현 가능한 20% 층화 서브샘플)을 먼저 실제로 생성한 뒤, 단계별 계획을 제시하겠습니다.

서브샘플 매니페스트가 생성되었습니다. 다운로드 가능하게 제공한 뒤 단계별 계획을 제시합니다.

# P1 파일럿 캘리브레이션 — 실행 명령어

논문 기준 경로(`syn/prolead/…`)로 작성했습니다. 리포지토리 구조에 맞게 변수만 조정하면 됩니다. **핵심 원칙: 파일럿 = 본 스윕의 시작.** 배치 1 완주 시간을 측정한 뒤 중단하지 말고 그대로 스윕을 이어가세요 (resume이 없어 죽이면 배치 1이 날아갑니다).

## 0) 경로 변수 설정

```bash
REPO=~/probing-resistant-masked-hardware        # 리포지토리 경로로 수정
LIB=$REPO/syn/prolead/library_yosys.json
NET=$REPO/syn/prolead/circuit_d2_struct.v
CFG=$REPO/syn/prolead/config_d2.json
RES=$REPO/syn/prolead/run_d2_result.json
LOG=$REPO/syn/prolead/run_d2_$(date +%Y%m%d_%H%M%S).log
```

## 1) 설정 사전 점검

```bash
jq . "$CFG" | grep -iE 'order|transition|simul|thread'
# 확인 항목: order=2, transitional=true, 시뮬레이션=64000, 스레드=물리코어 수
# (키 이름은 리포지토리의 config_d2.json에 있는 표기 그대로 확인)
nproc   # 코어 수 확인
```

## 2) tmux에서 시간·메모리 측정과 함께 실행

```bash
tmux new -s d2sweep
cd "$REPO"
/usr/bin/time -v PROLEAD -l "$LIB" -d "$NET" -c "$CFG" -r "$RES" 2>&1 | tee "$LOG"
# detach: Ctrl+B 누른 뒤 D  (프로세스는 계속 돕니다)
```

- PROLEAD 바이너리 이름/플래그가 다르면(예: `./release/PROLEAD`, `--library --design --config`) 기존에 쓰시던 호출 형태로 교체
- macOS에서는 `/usr/bin/time -v`가 없으므로 `time`만 붙이고, 메모리는 아래 모니터로 확인

## 3) 별도 터미널 — 진행 상황 감시

```bash
# 배치 진행·verdict 실시간 감시 (60초 간격)
watch -n 60 'grep -aiE "batch|simulation|leakage|okay" "$0" | tail -20' "$LOG"

# CPU/메모리 감시 (30초 간격)
watch -n 30 'ps -o pid,etime,%cpu,rss,comm -C PROLEAD'
```

PROLEAD가 타임스탬프를 안 찍으면 배치 완료 시각을 알 수 없으니, 실행 줄을 이렇게 바꾸면 매 줄에 시각이 붙습니다:

```bash
/usr/bin/time -v PROLEAD -l "$LIB" -d "$NET" -c "$CFG" -r "$RES" 2>&1 \
  | while IFS= read -r l; do printf '[%s] %s\n' "$(date +%H:%M:%S)" "$l"; done | tee "$LOG"
```

## 4) 배치 1 완료 후 — 실측값 추출

```bash
# 첫 번째 배치 완료 시각 (타임스탬프 붙인 경우)
grep -ai "batch" "$LOG" | head -5

# time -v 결과: 전체 경과시간 / 피크 메모리
grep -aE "Elapsed \(wall|Maximum resident set" "$LOG"
```

## 5) 판정 게이트 — 일정 재계산

```bash
T1=<배치1_실측_분>          # 예: 77
echo "34 batches => $(echo "scale=1; 34*$T1/60" | bc) hours"
```

**판정 기준**

| 실측 t_batch | 판정 |
| --- | --- |
| ≤ 90분 | 정상 궤도 → **그대로 계속 실행** (34배치 ≈ 51시간 이내) |
| 90분~3시간 | 느린 편 → 스레드 수/config 점검 후 계속 여부 결정 |
| > 3시간 또는 메모리 >16GB | 이 머신 부적합 → 더 큰 머신으로 이전, 또는 배치 크기 축소 옵션 가동 |
